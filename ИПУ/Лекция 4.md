* Транзакция по USB выглядят как: Token-Data-Handshake

* Виды токенов
	* OUT - следующий пакет будет содержать данные от хоста к устройству
	* IN - хост сообщает, что готов принимать от устройства пакет с данными
	* SOF - пакет отмечает начало временного фрейма/микрофрейма
	* EOF - пакет отмечает конец -//-

* Data
	* DATA0 - четный пакет данных
	* DATA1 - нечетный пакет с данными
	* DATA2 и MDATA - пакеты для высокоскоростной передачи

* Handshake
	* ACK - пакет получили
	* NACK - не готов обслужить предыдущий пакет, текущий пакет игнорируется
	* NYET

* Устройство-функция не может само отправлять пакеты, нужны команды от хоста
* Есть пространство на 127 адресов

* Передача данных идет кадрово
	* Один кадр состоит из SOF, транзакций (пакетов) и EOF
	* EOF - это не совсем пакет, а интервал времени, внутри которого передача пакетов запрещена.

* Размеры общих полей USB
	* Все пакеты начинаются с поля синхронизации (Sync).
		* Оно 8-битное при Low Speed и 32 бита при High Speed
	* Поле адреса устройства-функции ADDR
		* Ну он на 7 бит, но адрес 0 зарезервирован для Setup
	* Поле номера конечной точки (ENDPoint)
		* 4-битное. Для High Speed может быть 16 контрольных точек, для Low Speed - всего 4
	* Поле контрольной суммы CRC
		* Для токена контрольная сумма 5-бит, для данных - 16
	* Поле конца пакета EOP
		* Тоже скорее время тишины длительностью 2 бита несимметричного нуля

* Пакет Token
	* Sync -> PID -> ADDR -> ENDP -> CRC -> EOP
	* 24 бита

* Пакет Data
	* Sync -> PID -> DATA -> CRC -> EOP

* Пакет Handshake
	* Sync -> PID -> EOP
	* Всего 8 бит

* Пакет SOF
	* Sync -> PID -> Frame -> CRC -> EOP
	* Всего 24 бита

* Формирование кадра
	* Setup -> -> OUT
	* не уследил, хуле

* Транзакция SETUP
	* Token -> Data -> Status (передает устройство или хост, остальные два пакета - только хост)
	* Поле Data = 8-16 байт

* Транзакция OUT
	* Token -> Data -> Status ()
	* Размер Data - от 1 до 1023 байт

* Кадр чтения
	* Setup -> Транзакции IN
	* Да, их может быть несколько

* In
	* Token -> Data (передает или хост, или функция) -> Status
	* Пакет Data - от 1 до 1023 байт

* Про изохронные передачи (напомню, что там похуй на потерю единичных пакетов). Ну и еще они надолго занимают канад
	* Тут нет Handshake, только IN/OUT токен и Data

* Модель передачи данных в USB
	* Канал (Pipe) - это модель передачи данных между хостом и конечной точкой устройства
	* Их два типа
		* Поток - доставляет данные из одного конца в другой. Но всегда однонаправленно. Может реализовать три типа обмена: передача массивов, изохронная и прерывания
		* Сообщения - хост посылает запрос к точке, потом пакет данных и информация о состоянии конечной точки. Тут у нас передача с подтверждением. И еще тут общение двунаправленное

* Конфигурация устройств, подключаемых к USB
	1. Хаб информирует хоста путем смены своего состояния при опросе со стороны хоста. Устройство становится подключенным, а порт - отключен
	2. Хост уточняет состояние порта
	3. Хост сбрасывает состояние этого самого порта и дает разрешение
	4. Хаб формирует сигнал RESET для порта и переводит его в состояние ВКЛ. Тут адрес у устройства 0, оно может потреблять до 100 мА, чтоб запустить подключение на логическом уровне. У него теперь состояние POWERED (в своем начальное состояние)
	5. Это устройство доступно только по дежурному каналу щас, там передается максимальный размер поля данных пакета
	6. Теперь передается его уникальный адрес. Устройство становится в состояние Addressed
	7. Хост теперь считывает все параметры устройства, его конфигурацию и обеспечивает заявленный ток потребления
	8. Из считанной инфы хост подключает соответствующий драйвер и конфигурирует все имеющиеся на устройстве конечные точки. Устройство потребяляет теперь нужный по конфигурации ток. Устройство готово к использованию
* Устройство может не подключиться из-за нехватки питания от хоста/хаба.

# IEEE 1394

* Это попытка создать универсальный стандарт для быстродействующих интерфейсов, который мог бы обеспечивать работу с:
	* Мультимедиа
	* Накопителями
	* Формирователями
	* Визуализаторами
	* Синтезаторами данных

* Стандарт начали делать в 86, зарегистрировали его в 95. Участвовали в его разработки Apple, Compaq, Matsushita
* Тут нет связки с конкретным интерфейсом

* Apple в 92 его пытается реализовать под названием FireWire.
*  Sony его реализовывает в том же 95 под названием miniDV

* Цифровое видео - совокупность технологий записи, хранения, обработки и передачи изображения и звука
	* Тут уже видео- и аудио-сигналы кодируются и передаются после обработки АЦП в потоки видео- и звукоданных. Эта штука была тяжелой для интерфейсов
	* Так что начинается развитие сжатий. Как с потерями, так и без них

* Какая компрессия была (или дискретизация, я хз)
	* Картинка разбивается на три цветовых потока. Каждый из них обрабатывается и преобразовывается в более легковесные слои при помощи спец. констант

* Визуализация бывает построчной и чересстрочная (сначала нечетные строки воспроизводятся, потом четные)

* Проблема передачи видео - ебнутый битрейт (минимум 124 Мбит/с при хуевом разрешении, глубине цвета и дискретизации 4:1:1)
* Так что их надо сжимать. Там было много различных форматов, сжатие доходило до 5:1
