# Разбираем вторую работу

* Там предлагается делать ее через грамматики операторного предшествования:
	* Это грамматика предшествования, в которой отношения ТОЛЬКО между терминальными символами
	* НЕ МОЖЕТ СТОЯТЬ ДВА НЕТЕРМИНАЛА РЯДОМ
	* Строится в виде таблицы:
		* Строки - левые символы
		* Столбцы - правые символы
		* Ячейки - тип отношений

* Как строить:
	* Делается за 3 шага:
		* Для всех нетерминальных символов строятся множества крайних левых и правых символов
		* На основе их строятся для всех нетерминалов такие же, но уже чисто из терминалов
		* На основании множеств из п.2 строятся отношения предшествования для всех терминалов:
			* Дополнительно вводят дополнительно символы начала и конца строк. Они ставятся слева и справа

* Как строить множества крайних левых/правых символов:
	* В множество левых вносим все символы, которые являются крайними левыми в правой части правила
	* Аналогично с правыми
	* Если правый входит в множество левых, и он нетерминал, то он заходит в это множество
	* Аналогично с левыми
	* Повторять, пока не перестанут изменяться

* А с терминалами как?
	* Так же, только уже берутся ТОЛЬКО терминалы (в предыдущем этапе берутся вообще все)
	* Объединяем множества так же, как и в прошлом этапе

* А теперь строим матрицу:
	* Пример: G({+ - / * ( ) a b}, {S T E}, P, S)
	* P: (а я опять не успел это записать, но по описаниям этапов все достаточно просто)
	* ВАЖНО:
		* Если в одну клетку попало два символа, то тут два варианта (пустые клетки - норма):
			* Где-то ошибка в множествах
			* Грамматика не принадлежит грамматикам операторного предшествования
			* ВСЕ грамматики в лабе - точно операторного предшествования

* Строим оставную грамматику (все нетерминал заменяем на 1, но он будет типа с индексом)

* Синтаксический анализатор можно построить через прогу. Например, YACC - Yet Another Compiler Compiler (еще один компилятор компиляторов)
* YACC - не панацея. Он некоторые грамматики не может построить, так как он покрывает только LALR(1) грамматики
* Можно еще попробовать библиотеку LGR. Или какие-либо питоновские

* Для самого распознавателя нужен свой контейнер. Для синтаксического анализатора - это внутреннее представление программы.

# Внутреннее представление программы

* Некая структура данных, которая хранит содержимое исходной программы и ее структуру.
* Формирует на этапе синтаксического анализа
* Тут же выполняются первые шаги по семантике: разделяются все на две группы - операнды и операторы

* Формы внутреннего представления:
	* Машинно-зависимыеЖ
		* Зависят от архитектуры вычислительной системы, т.е. от ассемблеров
	* Машинно-независимые:
		* Не зависят от архитектуры
		* Пример: связанные списочные структуры, многоадресный код с явно/неявно именуемыми операциями

* Дерево операций:
	* одна из форм связанной списочной структуры
	* Два типа вершин: операторы и операнды
	* Операторы связывают между собой операнды
	* Если один оператор связан с другим, то результат низкого используется для работы с оператором высшего
	* Например, так можно избавитсься от скобок, которые только будут влиять на построение дерева
	* Удобны для иллюстрации
	* Для компилятора это накладывает дополнительные расходы. И еще надо обходить дерево циклически (слева направо, снизу вверх)

* Многоадресный код с явно именуемыми операциями (тетрады)
	* Выделяются операции и список операндов `операция(операнд1, операнд2, операнд3)`

* Многоадресный код с неявно именуемыми операциями (триады):
	* Только два типа: операнды и операции. Имеют вид `операция(операнд1, операнд2)`
	* Можно использовать в качестве операндов указывать ссылки

* Преимущества и недостатки многоадресного кода:
	* Преимущества:
		* подразумевают линейную последовательность команд
		* Анализ требуемых вычислительных ресурсов удобнее
		* Триады более современные и менее затратные
	* Недостатки:
		* Менять последовательность операций сложно
		* Сложность у этой штуки нелинейная

* Обратная (постфиксная) запись операций
	* Идея - операции пишутся после операндов. Имеют вид `операнд1 операнд2 оператор`
	* Приоритетов операций нет. Они не нужны, т.к. все операции записываются в порядке их выполнения
	* Скобки также используются только в определении порядка, но в записи не фигурируют
	* Как считать:
		* Считают при помощи линейного алгоритма на основе стека:
		1. Просматриваем запись
		2. Видим операнд - кладем в стек
		3. Унарный оператор - берем операнд из стека, выполняем операцию и кладем назад
		4. Бинарный оператор - берем два операнда из стека, считаем и кладем назад только результат
		* Главный недостаток - стек. Из-за него нельзя распаллелить вычисления
		* Поэтому она не применяется в практических компиляторах. Но в интерпретаторах - практически во всех используется. 

* Машинно-зависимые формы внутреннего представления программ
	* Компилятор должен использовать хотя бы одну из таких форм. В этом и его цель
	* Есть две основные формы: в виде машинных команд и в виде ассемблерного кода

# Подготовка и генерирование результирующего кода

* Семантический анализатор - рассматривает семантику (смысл) отдельных конструкций из всей исходной программы.
* Всю программу целиком семантически рассмотреть невозможно.
* Поэтому он работает в паре с синтаксическим анализатором
* Его функции:
	* проверка семантических соглашений входного языка
	* дополнение внутреннего представления программы действиями, неявно предусмотренные входным языком
	* проверка общих норм языков программирования

* Проверка семантических соглашений входного языка:
	* сопоставляется исходная программа  и семантические требования языка
	* Пример правил:
		* Есть метка, на которую есть ссылка - она должна присутствовать в программе
		* операнды должны иметь типы, допустимые для данных операций
		* Типы операндов должны быть согласованы
	* Если хотя бы одно не соблюдается - вызывается ошибка

* Дополнение программы неявными операциями:
	* Это операции, которые выполняются, но явно не указаны: преобразование типов или выделение памяти

* Проверка общих норм языков программирования
	* Пример таких норм:
	* Каждая переменная должна быть использована
	* Перед использованием переменной должно быть определено ее значение
	* Цикл должен иметь условие прерывания
* Конкретный перечень определяется разработчиком компилятора
* Чем больше проверок - тем лучше компилятор
* Зависят от норм, принятых в рассматриваемом входном языке.
